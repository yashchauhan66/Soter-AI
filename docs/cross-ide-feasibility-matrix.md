# SoterAI cross-IDE feasibility matrix

Status date: 2026-07-06. This is an engineering decision record, not a compatibility claim. A platform becomes supported only after its adapter builds, installs in a clean profile, completes a broker-backed scan, passes the canary privacy test, and produces a distributable package.

## Decision summary

SoterAI should use one local security plane (`@soterai/guard-core` plus the authenticated loopback broker) and small native adapters. The VS Code family can share one TypeScript/VSIX adapter when testing proves API compatibility. JetBrains products can share one Kotlin IntelliJ Platform plugin, subject to product-specific verification. All other targets need native adapters or a CLI fallback.

Scores are product priority from 1 (defer) to 10 (first). Complexity is relative adapter effort, not core-detector effort.

## Capability notes and architectural consequences

- “Terminal access” never means complete interception. The defensible MVP is explicit preflight checking, wrapped execution, and broker-side tool approval. An adapter must not claim to monitor commands it cannot observe.
- The broker listens only on loopback, requires authentication, redacts its ledger, and remains the enforcement boundary. IDE storage holds only a broker credential or pairing material when a platform provides a suitable secure API.
- Webviews/panels display redacted findings and references. Raw source, prompt, secret, and terminal output are not telemetry and are not sent to SoterAI Cloud by default.
- Remote IDE modes (SSH, containers, WSL, Gateway, hosted Jupyter) require an explicit topology: run the broker beside the extension host, or use an authenticated tunnel/pairing design. `localhost` is not assumed to mean the user's laptop.
- Compatibility is package- and version-specific. Shared code does not turn Cursor, Windsurf, Rider, or all Open VSX consumers into automatic support claims.

## Recommended implementation order

1. Keep the existing VS Code adapter and produce one audited VSIX for VS Code, Open VSX, Cursor, and VSCodium testing.
2. Build one IntelliJ Platform adapter against the broker and verify it first in IntelliJ IDEA and PyCharm or WebStorm.
3. Build Neovim and Sublime adapters, both broker-first with CLI fallback.
4. Build Visual Studio after choosing the supported SDK surface from an executable prototype.
5. Prototype JupyterLab's local-versus-remote broker topology before committing to marketplace support.
6. Defer Eclipse and Vim to basic adapters. Treat Zed and Emacs as feasibility prototypes, not launch support.
