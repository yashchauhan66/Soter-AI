# Bounded secretless operation broker

`SecretlessOperationBroker` is a host-side capability for one reviewed HTTPS JSON GET. It never gives the agent a credential or accepts an agent-supplied URL, header, query, body or HTTP method. The owner configures an exact operation ID, account, resource, URL and response-field allowlist. It is a finite operation mechanism, not a general cloud API proxy.

The trusted host creates a review with `prepareReview(operationId, binding)`, displays its exact operation and binding to the owner, and calls `approve(review)` only after owner approval. Approval accepts the original prepared object, has a deadline and returns an opaque grant. Each grant binds the operation configuration, account/resource, allowed fields, session ID, image digest, artifact digest and policy digest. The agent may spend the grant once through `execute(grantId, binding, signal)`. Consumption occurs before credential acquisition, including attempts with a changed binding.

Reviews and local grants expire after 30 seconds. Each execution has a maximum five-second deadline, a 64 KiB response limit and a 16 KiB projected-output limit. At most four calls may run concurrently; issuer or transport promises that ignore cancellation still count against the outstanding-work limit. Session revocation permanently invalidates that session in the broker, cancels pending calls and removes pending reviews/grants. Start a new session with a fresh identifier to obtain new authority.

## Credential-provider contract

An issuer integration implements the host-only `CredentialLeaseProvider.acquire(request, signal)`. Its result contains the bearer token, its **actual issuer expiry**, the exact operation digest/account/resource, output-secret registrations and a disposal callback. The broker refuses expired credentials, non-finite expiry, credentials with more than 15 minutes remaining, a mismatched scope and unsafe header bytes. Local grant expiry does not make a stored long-lived token short-lived. A real issuer adapter must attest actual scope and expiry; the broker cannot establish those issuer facts by trusting an arbitrary timestamp supplied by untrusted code.

The provider and transport are injected only by trusted host code. Neither is an isolated-agent capability. Provider-specific account binding, token issuance/refresh, OIDC validation and resource-scope enforcement must be implemented and verified by that issuer adapter. The optional HashiCorp Vault integration below implements one concrete issuer. It does not replace the existing EC2/OIDC implementation or establish a general cloud-provider integration.

## Optional HashiCorp Vault integration

The extension registrar `registerSecretlessOperationCommands(context, refresh)` returns the trusted host bridge used by an isolated session: `list()`, `policyDigest()`, `executeApproved(id, binding, signal)` and `dispose()`. Each execution prompts the owner with the exact GET URL, account/resource, allowed fields, token role/policies, maximum lifetime and session/image/artifact/policy binding. The guest receives only the checked operation result.

Configure it through **SoterAI: Configure Secretless Vault Operation** (`soterai.configureSecretlessVaultOperation`). Native inputs collect one trusted HTTPS Vault origin, token role, exact expected effective policy names, same-origin `/v1/` GET path, top-level scalar response fields and a lifetime between 10 and 120 seconds. The issuer bootstrap token is entered in a password field and stored only in VS Code SecretStorage. Commands reject arguments; neither guest IPC nor command parameters can supply credentials or approval. Configuration metadata goes in globalState, and setup makes no network request or issuer-verification claim.

After native approval, `VaultTokenLeaseProvider` calls exactly `POST /v1/auth/token/create/<configured-role>` with the bootstrap in `X-Vault-Token`, requested policies, `ttl` and `explicit_max_ttl` at the configured bound, `num_uses: 1` and `renewable: false`. It accepts only a distinct issued service token whose returned `auth.lease_duration`, `auth.policies`, `auth.num_uses` and `auth.renewable` match the reviewed constraints. Expiry is measured conservatively from the beginning of issuance. Only that issued token reaches the exact approved GET via `X-Vault-Token`; the bootstrap is never used for the resource read. Both tokens are registered for output checks.

Disposal attempts `POST /v1/auth/token/revoke-self` with the issued token, under a separate 1.5-second bound. This is best effort: a one-use token may already be consumed, the connection may fail or ACLs may deny self-revocation. The checked issuer lifetime remains the expiry bound. Failed or withdrawn issuance also attempts revocation if an issued token was received. Cancellation does not expose a late issuer response.

The Vault administrator must configure the token role and ACLs. The bootstrap should be limited to creating tokens for that role. The role must permit only the reviewed resource-read policies, enforce the token lifetime and return the expected effective policy set, including `default` if present. The extension checks the response and request restrictions; it trusts the selected Vault server to enforce actual ACLs, token-use counts and expiry. Namespace headers, custom CA overrides, redirects, queries and renewal are unsupported.

One supported finite example is `/v1/sys/health` with `initialized,sealed,standby` as allowed fields. This endpoint can be public under Vault's server policy; successful use does not independently prove that an ACL denied other resources. Nested KV responses are unsupported by the current scalar-field contract. A real administrator must separately verify the intended role and resource ACLs before relying on them.

`soterai.secretlessOperationStatus` reports stored configuration only. `soterai.removeSecretlessVaultOperation` requires native confirmation and removes the public configuration and its SecretStorage bootstrap. Missing configuration, missing bootstrap custody, a cancelled approval or mismatched issuer response remains unavailable. No dummy credential provider is installed.

## Request and response restrictions

The default transport uses Node HTTPS with certificate verification, a fresh connection, fixed `GET`, fixed `Accept`/`Accept-Encoding` headers and the leased bearer header. It does not follow redirects, retry, inherit proxy environment settings or accept custom CA/DNS options. URLs require HTTPS, a canonical public-looking hostname and no query, fragment, user information or custom port. Literal IP addresses and local/internal hostnames are unsupported. The exact owner URL is the authority; this is not a general SSRF defence for arbitrary caller URLs.

Only HTTP 200 identity-encoded `application/json` is accepted. Strict bounded JSON parsing rejects duplicate keys, excessive nesting, excessive nodes and invalid UTF-8. Every selected response field must exist and contain a scalar string, number, boolean or null; nested selected values are unsupported. Other fields are omitted. The whole response, decoded JSON string leaves in response order, and the final serialized result are checked against the credential and registered output secrets. Ambiguous known short output values withhold the operation result. Provider errors and rejected responses become a fixed `WITHHELD` result with no upstream body, headers, credential or exception text.

Known-secret recognition is bounded and does not promise detection of every transformation or cross-call fragment. The trusted service and allowlisted fields remain part of the security design. An arbitrary powerful credential should not be used where the issuer supports a resource-scoped short-lived credential.

## Validation scope

The focused broker and transport suites cover single use, concurrent reuse, every binding field, review/grant/issuer expiry, issuer-scope mismatches, cancellation and revocation, late lease disposal, stalled-call bounds, redirect refusal, TLS/request options, response size/type/compression/JSON boundaries, field projection and raw/encoded/split known credentials. Additional Vault-provider and native-command tests exercise configuration custody, per-use consent, exact token-creation requests, issuer policy/lifetime/use/type refusal, same-origin read binding, bootstrap/issued-token output refusal, cancellation and removal. Transport tests use injected request fixtures and synthetic credentials. They make no external requests and do not certify a real Vault server, cloud account or native isolated-agent deployment.
