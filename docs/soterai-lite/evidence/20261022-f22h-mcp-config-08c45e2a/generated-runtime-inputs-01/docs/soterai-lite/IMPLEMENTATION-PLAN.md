# SoterAI Lite implementation plan — one feature at a time

Date: 13 October 2026. Plan version: 1. Scope: existing non-VM functionality plus the remaining Lite upgrades. This is a plan, not an implementation or a passing product report. Final rating: **PENDING until completion and required verification**.

The user's latest instruction controls execution: **finish and test one feature, then start the next**. Implementation has one active feature at a time. Test specifications and adversarial reviews may run in parallel; production implementation may not. Existing working-tree changes and the tested dated 0.6.3 candidate are the starting inputs; they are not a newly completed Lite split.

## Product contract

Lite installs as one VSIX and starts local checks automatically. Advertised local functionality must not require administrator rights, VM software, a controller service, npm commands, accounts or new external software. Protected file selection, access approval and a short reviewed setup are user interactions, not extra installations. Vendor integration changes and vault migration require explicit review; they must never be silently applied.

Ordinary restrictions stay denied by default. The owner may approve one saved-file safe view. Sensitive approval authorizes only a masked representation: dotenv key names with every value masked; other sensitive formats remain withheld unless a separately tested schema parser is enabled. No global original-secret permission is added.

Lite's supported threat model is cooperative AI using documented, verified controls and managed routes. It cannot promise denial of arbitrary same-user native reads, unrelated shells, independent uploads or other extensions' original buffers. Project-only scope does not change that. A custom editor controls its own document model/rendering, and output masking cannot undo an exfiltration that occurred before stdout. Those limitations stay visible in the UI and final report.

Full is a separate scaffold with a dependency on Lite; no VM/controller/mTLS/full-only protocol code ships in Lite. A stronger independent boundary is not covertly added to this install-only product. Unknown confidential prose, arbitrary transformations, past exposure and process-memory inspection remain explicitly limited.

Official references checked for this plan: [VS Code extension runtime permissions](https://code.visualstudio.com/docs/configure/extensions/extension-runtime-security), [custom document vs TextDocument editor](https://code.visualstudio.com/api/extension-guides/custom-editors), [terminal API](https://code.visualstudio.com/api/references/vscode-api#Pseudoterminal). Vendor/version-specific mechanisms must be verified against installed source/docs during their own work card; current generic documentation is not evidence for an older installed version.

## Mandatory completion gate for each work card

Before starting, name the feature ID, user requirement, frozen leak-check IDs, implementation scope, proposed flag, affected source modules and its exact acceptance checks. Inspect those files first. Any scope change gets a written reason; no passing item is erased.

For a behavior feature:
1. Write meaningful synthetic regression/acceptance tests before changing behavior; retain the expected failing result where reachable.
2. Implement only that feature behind its flag. Reuse the existing reader/policy/guard core rather than create a competing authority.
3. Run focused unit/property/fuzz checks appropriate to the feature, positive public controls and negative secret controls.
4. Typecheck/build; create a uniquely named VSIX and inspect its actual entry list and SHA-256. No old normal-filename package may substitute for it.
5. Run affected consent/editor/terminal/proxy workflows in an isolated actual VS Code host against that exact installed VSIX; record its loaded runtime identity. A mock/stub proves only its component.
6. Test cancellation, outage/error and safe withdrawal/rollback. Unavailable features must not return originals. Policy/file/workspace/recipient drift invalidates pending approvals.
7. Review results, retain failed attempts, append the ledger receipt and commit the scoped feature locally. Required checks must PASS for its declared supported scope before the next card starts.

Planning/scaffold/documentation cards use schema/import/manifest/package-integrity checks appropriate to their scope, not invented behavioral tests. A pure shared utility can complete its utility contract through real component checks; it cannot be promoted to a tested AI adapter until the later actual-tool gate passes. Explicitly separate this from complete user-demand satisfaction.

At P03, lock optional-runtime availability and tool applicability before catalog freeze. An absent optional shell/tool is visibly NOT_TESTED/NOT COVERED, never DONE; exclude only that optional card from the supported execution queue with a recorded reason, while retaining it in the requested-feature inventory and final remaining-work list. Required product behavior cannot be made optional to bypass a failure. Update the planning queue's supported execution dependencies at P03 before implementation starts.

Feature task states: PLANNED, ACTIVE, VERIFYING, DONE. Evidence labels remain PASS / FAIL / INCOMPLETE / UNTESTED / STATIC-ONLY / UNVERIFIED / NOT-RUN / BLOCKED-HUMAN. A stub, merely present API, stale bundle, skip, unverified vendor hook or untested required path cannot become DONE for that behavior. Optional unavailable platforms remain named NOT_TESTED and outside the advertised supported set.

Actual installed-tool execution against a supported synthetic loopback provider may satisfy local adapter route checks without a real provider login. If the tool cannot actually execute a required route without authentication, its card stays ACTIVE/BLOCKED-HUMAN and implementation stops at that card for user action. Do not mark it DONE by substituting a mock or scheduling its required test for L6. Required external-provider smoke remains a later human acceptance gate under the no-external-payload rule. This early human dependency follows the latest strict serial instruction; it does not authorize agent login or credential use.

If shared code changes, reopen affected earlier verification before the next feature. Permit at most three improvement rounds for an eligible failure/partial item. If a mandatory behavior still cannot pass, leave the card open and report the blocker; do not silently start another feature or claim all requirements are complete. Scope exclusions must follow the frozen threat model and applicability rules, never score optimization.
