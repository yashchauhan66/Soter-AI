## Established harness delay

The launcher invokes `stable()` again between Code spawn and listener-helper spawn. This took 2.691 seconds. The helper then repeats large executable hashes, full descendant CIM queries, and TCP-module startup before emitting listener custody. It took another 16.966 seconds and outlived Code. Thus the harness provides no renderer observation during the startup trust window.

A defensible successor can pre-warm and validate an owned listener helper before Code launch, then emit an **early exact-root listener receipt** after validating the captured root PID, creation time, executable, exact synthetic profile argument, numeric loopback port, and root ownership of that listener. Only that verified endpoint may be attached. The same helper must continue the existing full-tree custody, and phase acceptance and post-close absence must still require it. Source/vendor revalidation belongs before launch and after attach; it must not be omitted from acceptance.

The earlier attach should record bounded startup-dialog/input metadata before acting: whether the checkbox is checked, event kind, trusted-event flag, fixed target category, and timestamp. It must not capture general typed text, alter the prompt, or synthesize trust. A disappearing dialog or premature grant still fails. This improves the missing observation; it is not claimed to fix the unexplained trust trigger.
