## Protected second account/session and management

**FACT — accessed 2026-10-09.** Windows supports switching accounts while their applications remain running. Microsoft recommends a standard primary account with separate administrative authorization when needed. Source URLs: [Windows account switching](https://support.microsoft.com/en-US/accounts-billing/security/user-account-access-in-windows), [UAC behavior](https://learn.microsoft.com/windows/security/identity-protection/user-account-control/how-user-account-control-works).

**INFERENCE — Required topology.** P is a separately managed standard account and interactive session for protected editing; U remains hostile. S owns protected state, M controls deployment and network/VM configuration. P must not run AI extensions, arbitrary workspace tasks or unreviewed editor helpers. Neither U nor guest A may change P's installed editor, its parents, recovery state or admission policy. Sharing an editor profile under the same U cannot meet these responsibilities. An ordinary UAC consent dialog is not the item-bound C approval contract.

**INFERENCE — `.env` editing.** The human switches into P, opens the protected editor, edits the S-managed item under its scoped edit lease, saves a new protected revision and returns to U/A's sanitized workspace with opaque placeholders. Plaintext `.env` is never opened in U's AI-connected window. Clipboard history/sync, resource redirection, console bridges, indexing and recovery copies must stay in the protected scope. Existing plaintext/history copies keep legacy enrollment pending. A separate account by itself does not establish display, process, memory, accessibility or clipboard isolation; A02/A06/A14/A30 remain UNTESTED.

**SPECULATION — UX estimate.** Occasional credential changes may tolerate session switching; repeated secret edits, mixed public/private debugging and frequent grants may be disruptive. No task timing, accessibility or user adoption study was run. A native trusted editor would reduce trusted dependencies at the cost of editor features; a managed VS Code session requires more admission and recovery review.

## Witness W and policy continuity

**FACT — accessed 2026-10-09.** Rekor documents a verifiable log whose consistency can be monitored, plus separate witness/auditor tooling. Azure Blob immutable storage documents time-bounded WORM retention. Source URLs: [Sigstore Rekor](https://docs.sigstore.dev/logging/overview/), [Azure immutable storage](https://learn.microsoft.com/en-us/azure/storage/blobs/immutable-storage-overview).

**INFERENCE — W choices.** A separately administered local witness/service outside guest snapshots, a separately managed existing device, or a private external checkpoint service are candidate locations. W must retain accepted policy/audit sequence and digest, authenticate S/M enrollment and recovery, and make older policy or missing continuity enter RECOVERY_LOCKED. A signed JSON file or repository hash under U is review provenance, not independent W. WORM retention alone neither proves the latest accepted sequence nor supplies grant authorization; a public transparency service could leak metadata and is not selected.

**SPECULATION — W cost.** Existing independently managed hardware may need no new purchase but still needs engineering, backups and availability support. A small external service may be inexpensive; no provider quote, account, regional price, SLA or retention bill was established. Keep recurring cost UNKNOWN rather than manufacturing a subscription total. **INFERENCE:** Sharing C's physical device with W can reduce purchases but couples availability/recovery; it needs an explicit fault/rollback review. Witness loss pauses protected releases rather than weakening policy. A13/A21/A26 remain UNTESTED.

## Mandatory host egress E and adoption

**FACT — accessed 2026-10-09.** Windows Filtering Platform exposes filtering at multiple network-stack layers. WFP documentation distinguishes dynamic, static, persistent and boot-time objects and their lifetimes. Source URLs: [WFP overview](https://learn.microsoft.com/en-us/windows/win32/fwp/windows-filtering-platform-start-page), [WFP object management](https://learn.microsoft.com/en-us/windows/win32/fwp/object-management).

**INFERENCE — Deployment cost.** E must cover hostile native U processes and their helpers as well as A/D guests. It needs M-owned policy, startup/outage behavior, IPv4/IPv6, DNS, UDP/QUIC, proxies, redirects, local services and delegated tool routes, with a narrow authenticated gateway. A container proxy alone leaves native agents outside coverage. Persistent filtering APIs provide mechanisms, not evidence of comprehensive mediation. No rule, callout, driver or firewall deployment occurred; A12/A16/A17/A19 remain UNTESTED.

**INFERENCE — UX impact.** Unapproved package downloads, model endpoints, tool services and developer tunnels would be denied; adding approved public destinations requires the trusted administrative workflow. Generic HTTPS relay permission must not authorize protected export. Protected release consent binds its item and operation separately. E downtime means blocked protected work; the user needs a clear outage/revocation-pending status and a public-only path that cannot access protected assets.

**SPECULATION — Adoption.** Full Tier 3 likely suits users willing to accept managed OS/network policy, session switching, device confirmation and limited endpoints. Ordinary extension installation offers much lower friction but cannot support the same threat-model claims. No conversion rate, support cost, network compatibility or latency was measured.

## Approval and rollback boundary

**INFERENCE — Prepared decision.** Full / partial / defer describes the next authorized scope, not a security score. Approval of a planning option must not be interpreted as permission to create accounts, enable features, deploy VMs, alter firewall/drivers, enroll hardware or change the normal profile. Any later deployment needs its concrete object list, backups, expected-result assertions and rollback reviewed first.

**INFERENCE — Protective rollback.** Failed prerequisite or rollback stops grants/publication and keeps protected custody and denials. It must never reconnect private D to networking, mount secrets into U/A, downgrade C to a modal, accept stale W state or disable mandatory E while protected content is reachable. Migrating plaintext back into the ordinary workspace is a new disclosure decision. Keeping a public-only mode requires a clear limitation label, not a green protected state.

**INFERENCE — Completion.** B5 document/metadata preparation is complete; deployment feasibility is INCOMPLETE and security acceptance is UNTESTED. No product behavior changed, so no feature flag or runtime rollback was introduced. Source URLs were accessed on 2026-10-09; local observations have exact UTC timestamps in their evidence. Builder preparation is not independent verification.
